# 技能来源账本（Skill Provenance Ledger）

本应用如何将本地已安装技能与商店条目（`owner/repo/slug`）关联起来——
在 `agents-skills` 0.13 移除 lockfile（连同最后的安装来源记录）之后。

英文版：[skill-provenance.md](./skill-provenance.md)

## 问题

商店索引用规范 id `{owner}/{repo}/{slug}` 标识每个技能。而本地技能只是
`~/.agents/skills/<name>` 下的一个目录，其 `SKILL.md` frontmatter 只含
`name` 和 `description`——没有任何来源信息。slug 是唯一的公共键，因此
来自不同仓库的同名技能无法与已安装的那个区分开。

## 设计：应用级账本

应用自行维护一份记录——**来源账本（provenance ledger）**——为一个 JSON 文件：

```
~/.agents/skills/.skill-one.json
```

```json
{
  "version": 1,
  "skills": {
    "pdf": {
      "repo": "anthropics/skills",
      "slug": "pdf",
      "installedAt": "2026-09-13T08:00:00.000Z",
      "hash": "9a1f…"
    }
  }
}
```

可选的 `hash` 是建立关联时记录的**商店侧**内容哈希：原生安装记录安装
时索引条目的 `rev`，哈希自动关联记录命中的 `rev`（按匹配定义，它与本地
内容哈希必然相等）。它是版本标记，不是本地文件的描述——刚克隆的副本
跟随 repo HEAD，可能领先于索引快照，若存计算目录哈希会与 rev 永久不一致，
污染更新信号。将来的更新检查只需比较记录的哈希与索引最新 rev：不同即
表示安装后商店发布了新版本。本地编辑对它不可见，这是有意为之。

关键特性：

- **每次安装成功后写入**（`installSkillFromSource`），以技能名为键；
  重复安装会覆盖旧条目。
- **对账时清理。** 每次加载已安装列表时，删除磁盘上已不存在的技能对应
  的条目，因此在应用外删除的技能不会再声称有来源。
- **卸载时清除。**
- **两端均为尽力而为。** 账本写入失败绝不会导致安装或卸载本身失败；
  文件缺失或损坏时降级为空账本（即仅按名称匹配的旧有行为）。
- **对其他工具不可见。** 该文件是没有 `SKILL.md` 的隐藏点文件，
  `agents-skills` 的目录扫描会完全忽略它。

### 存储位置的选择

账本与它描述的技能放在一起（而非 Tauri 应用数据目录），这样对账就是
账本↔磁盘的直接比对，且应用重装后关联依然存在。代价是：把 `~/.agents`
移走会丢失映射——这是可接受的，因为技能本身也随之移动，账本会由后续
安装重建。

### 后端接口

Rust 侧保持极薄——两个固定路径的文件命令，不了解账本 schema（解析、
合并与清理都在 `src/lib/provenance.ts`）：

| 命令 | 行为 |
| --- | --- |
| `read_provenance` | 读取原始文件内容；账本不存在时返回 `null` |
| `write_provenance` | 全文档替换，原子写入（临时文件 + 重命名） |

两者都在内部解析路径（`<home>/.agents/skills/.skill-one.json`），
不接受调用方控制的路径。

## 消费方

- **安装按钮**（`skill-install-button.tsx`）：磁盘上存在同名技能，且
  账本条目的 `repo` 与商店条目一致（或没有账本条目——来源未知时退回
  仅按名称匹配）时，才显示"已安装"。来自不同仓库的同名技能仍可安装。
- **我的技能页**（`my-skills-page.tsx`）：有账本条目的卡片显示来源仓库
  与 owner 的 GitHub 头像；详情抽屉链接到源仓库，而不是显示"本地安装"。
  工具安装的技能没有条目，保持本地安装的展示。

## 关联其他工具安装的技能

账本只覆盖本 App 的安装。其他工具安装的技能（`npx skills` CLI、手动
复制）通过另外两层完成关联，由同一个对账查询驱动
（`use-skill-provenance.ts`、`lib/link-suggestions.ts`），且仅在注册表
快照就绪时运行：

### 第一层：哈希自动关联（确定）

商店索引带有每个技能的 skills.sh 上游内容哈希：对每个文件按
`相对路径 + 0x00 + 文件字节 + 0x00` 拼接后取 SHA-256，文件按大小写
不敏感的 ICU 排序（`Intl.Collator("en", {sensitivity: "base"})`）——
**不是**字节序（字节序只能复现约 40% 的哈希）。廉价的筛选先行：索引里
没有同名条目的技能直接跳过——就是普通本地技能，不做磁盘遍历。否则
后端为已安装技能计算同样的哈希（`compute_skill_hash`，
`skill_hash.rs`）；与同名条目的 `rev` 相等即为内容级同一性，因此直接
写入账本，与原生安装完全一致——无需用户操作，卡片立即显示来源仓库。

已对发布快照实测验证：本地重算 51/51 个抽样技能全部与索引匹配。
不匹配是预期行为并已处理：镜像快照可能省略本地克隆含有的文件
（媒体/二进制）、`safeSegment` 会重写特殊路径字符，或本地副本的版本
与索引快照不同。未命中按注册表 epoch 备忘，对账查询不会重复哈希
已知死路。

### 第二层：候选排序 + 用户确认（启发式）

对剩余技能，将同 slug 的注册表条目按描述相似度排序（token Jaccard；
中文按字符 bigram 比较，与共享搜索索引同一技巧），在卡片上以
"确认关联"入口呈现。对话框最多列出 5 个相似度 ≥ 0.3 的候选并标注
相似度百分比——明确仅为参考而非证明：fork 共享描述，100% 相似度
也不能*认定*同一技能。用户选择之前不写入任何内容；确认结果与原生
安装无差别地写入账本。

为什么不在 100% 相似度时自动关联？对发布快照（8993 个技能）的实测：
549 个 slug 由 ≥2 个仓库发布，其中 171 个（31%）存在 ≥2 个*不同*仓库
携带逐字节相同的描述——涉及 525 个技能。每个描述完全相同的簇都跨越
多个仓库（fork 会原样照抄 frontmatter），因此完美的描述匹配在结构上
就是歧义的：它选中 fork 和选中本体的概率一样，且错误是静默的（错误的
来源链接、错误的更新流），用户收不到任何纠错信号。

刻意的非目标：相似度绝不静默自动关联（错误的"已安装"标注比没有更
糟），也不设任何让启发式绕过用户的阈值。
