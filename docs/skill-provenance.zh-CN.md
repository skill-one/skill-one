# 技能来源账本（Skill Provenance Ledger）

本应用如何将本地已安装技能与商店条目（`owner/repo/slug`）关联起来——
在 `agents-skills` 0.13 移除 lockfile（连同最后的安装来源记录）之后。

英文版：[skill-provenance.md](./skill-provenance.md)

## 问题

商店索引用规范 id `{owner}/{repo}/{slug}` 标识每个技能。而本地技能只是
`~/.agents/skills/<name>` 下的一个目录，其 `SKILL.md` frontmatter 只含
`name` 和 `description`——没有任何来源信息。slug 是唯一的公共键，因此
来自不同仓库的同名技能无法与已安装的那个区分开。

## 设计：应用级账本

应用自行维护一份记录——**来源账本（provenance ledger）**——为一个 JSONL
文件：一行文件头，其后每个技能一行，后行覆盖前行：

```
~/.agents/skills/.skill-one.jsonl
```

```jsonc
// 文件头，永远在第一行：下方待确认记录所对应的注册表快照身份。
{"kind":"meta","index":"\"a1b2c3\""}

// 来源记录：技能已与商店条目关联。`via` 说明关联的建立方式——`install`
// （本应用自行安装）、`confirm`（用户从候选中选定）或 `description`
// （自动关联）——详情抽屉据此区分「商店安装」与「已关联的第三方副本」。
{"kind":"source","name":"pdf","repo":"anthropics/skills","via":"install"}

// 待确认记录：仍在等待用户决定的建议。`candidates` 是排序后的同名候选，
// `key` 是排序输入的摘要，`fingerprint` 是计算时的仅 stat 目录状态。
// `repos` 是用户解除过的仓库：自动关联不会再自行关联它们，但用户仍可手动选回。
{"kind":"pending","name":"my-tool","key":"1a2b3d4d5e6f7081","fingerprint":{"mtimeMs":1738022.4,"size":48213},"candidates":[…],"repos":["someone/skills"]}
```

每一行都自报家门：`kind` 区分记录形状，因此一条记录按它声称的身份被读取，
而不是靠「碰巧存在哪些字段」来推断。文件头的 `index` 是所服务快照的
`etag`（`IndexInfo.etag`——etag 相同即索引字节相同），于是「这份排序缓存
还有效吗」变成与当前所服务快照的一次比较。它刻意**不是**客户端的 `epoch`
计数器：后者每次进程启动都从零重启，若把它落盘，等于用一个月的旧记录去
验证今天的数据集。文件头若未指名快照，则不为任何缓存背书：其记录一律
重算，不予采信。

账本只存两类东西，都有过被删的字段，各有各的原因——要么无人读取，
要么无从比较：

- **不存时间戳。** 账本从不展示安装时间——UI 读的是已安装记录上文件系统
  自己的时间戳——而对第三方副本，应用唯一知道的时间是它写入*关联*的时刻，
  那并不是安装时刻。关联发生在何时是活动日志的职责。
- **不存内容哈希。** 注册表已不再发布逐技能哈希，落盘的哈希没有任何比较
  对象。计算它的那一层（`analyze_skill` 与 `skill_hash.rs`）随之删除：
  守护缓存排序的是仅 stat 的 `fingerprint`，它回答同一个问题（目录是否
  变了），却不读一个文件字节。这同时意味着，对十几个未关联技能跑一轮
  关联，现在花的是十几次 stat 遍历，而不是十几次全量内容读取。
- **不存死路。** 没有同 slug 注册表条目的技能不值得占一行：重算它只是一次
  内存查询，而存下来每次快照变更都要整批重写。值得落盘的是昂贵的
  （一份排序）和属于决定的（一次解除），因此某个名字从账本里消失是格式
  在正常工作，而不是数据丢失。

损坏或读不懂的行直接跳过——按行容错就是全部的安全网：本构建读不了的一行
（格式错误、手工改坏、或由它不认识的格式写入）会被丢弃，文件的其余部分
照常应答。这里没有格式版本号，也没有更旧的形状要认。格式变更就是整文件
替换：某个构建读得了的，它也写得出来。

关键特性：

- **每次安装成功后写入**（`installSkillFromSource`），以技能名为键；
  重复安装会覆盖旧条目。
- **对账时清理。** 每次加载已安装列表时，删除磁盘上已不存在的技能对应
  的条目，因此在应用外删除的技能不会再声称有来源。
- **卸载时清除。**
- **两端均为尽力而为。** 账本写入失败绝不会导致安装或卸载本身失败；
  文件缺失或损坏时降级为更少的记录（即仅按名称匹配的旧有行为）。
- **对其他工具不可见。** 该文件是没有 `SKILL.md` 的隐藏点文件，
  `agents-skills` 的目录扫描会完全忽略它。

### 存储位置的选择

账本与它描述的技能放在一起（而非 Tauri 应用数据目录），这样对账就是
账本↔磁盘的直接比对，且应用重装后关联依然存在。代价是：把 `~/.agents`
移走会丢失映射——这是可接受的，因为技能本身也随之移动，账本会由后续
安装重建。

### 后端接口

Rust 侧保持极薄——固定路径的文件命令加上目录身份，不了解账本
schema（解析、合并与清理都在 `src/lib/provenance.ts`）：

| 命令 | 行为 |
| --- | --- |
| `read_provenance` | 读取原始账本内容；文件不存在时返回 `null` |
| `write_provenance` | 全文档替换，原子写入（临时文件 + 重命名） |
| `open_provenance_dir` | 在系统文件管理器中显示账本所在目录（全局技能目录） |
| `skill_fingerprint` | 仅 stat 的目录指纹（最新 mtime + 总大小，不读文件字节）——守护已存排序的那一位 |

所有命令都在内部解析路径（`<home>/.agents/skills/…`），
不接受调用方控制的路径。

### 开发者查看器

设置 → 开发者 会打开 `developer-dialog.tsx`——一个只读的账本调试界面：
它按文件的真实样子完整渲染——每行一张卡片、保持文件顺序、重复条目保留、
所有字段全部展示（schema 未来新增的未知字段也会以原始键名出现）、损坏的
行显式标记并附原文而不是跳过——另提供原始 JSONL 视图与「在文件夹中显示」。
它刻意**不**复用 `parseLedger` 的容错合并语义：应用必须决定依据什么行动，
但当开发者想问「这个技能为什么认为自己来自 X」时，应用没有采纳的那条记录
同样需要看见。

## 消费方

- **安装按钮**（`skill-install-button.tsx`）：磁盘上存在同名技能，且
  账本条目的 `repo` 与商店条目一致（或没有账本条目——来源未知时退回
  仅按名称匹配）时，才显示"已安装"。来自不同仓库的同名技能仍可安装。
- **已安装页**（`installed-page.tsx`）：同一份安装列表有两种形态——仓库卡片（卡片）与 skill 行（列表，按热度/按安装时间/按 Token 占用排序），
  每种形态对同一技能的呈现完全一致，因此技能在哪里读起来都一样。有账本条目的行显示 owner 的
  GitHub 头像（卡片元信息行上的作者头像，仓库名由它的浮窗报出——卡片本身
  不再打印仓库文本），以及详情抽屉的仓库行；详情抽屉链接到源仓库，而不是
  显示"本地安装"。
  记录的来源还会反查回它的注册表条目（`use-installed-store-entries.ts`，
  底层是 worker 的 `lookupSkills`）——商店的分类徽章与安装量正来自那里，
  磁盘上的记录本身没有这两项；没有这一步，已安装列表只能渲染出「商店的
  卡片、但这两格是空的」。反查不到来源的技能（工具安装，或索引已不再收录）
  保持本地安装的展示且不显示安装量，而不是伪造一个 0；这一区分由
  `SkillView.storeBacked` 记录，卡片与详情抽屉按同一规则读取。作者头像是
  唯一不受此影响的部分：即便注册表里没有条目，账本仍能担保它的仓库。
  而卡片的图片位在无法定址封面时回退为技能自身的首字母。
  仓库卡片的底栏打开的是「这份列表眼中的该仓库」
  （`/installed/repo/owner/repo`）：账本归到该仓库的那些安装，用已安装列表
  自己的那套行内控件列出；商店为同一仓库提供的其余目录，则放在列表底部一个
  控件之后。商店自己的那一页（`/repo/owner/repo`）仍在其后一步——这正是
  卡片不再直接通向它的原因。

## 关联其他工具安装的技能

账本只覆盖本 App 的安装。其他工具安装的技能（`npx skills` CLI、手动
复制）由同一个对账查询完成关联（`use-skill-provenance.ts`、
`lib/link-suggestions.ts`），且仅在注册表快照就绪时运行。流程按成本
从低到高排列。

### 第一步：同名筛选

索引里没有同 slug 条目的技能就是普通本地技能：无从关联，也完全没必要
去看它的目录。这只是一次针对 worker 搜索索引的内存查询——也正因此，它的
「没有同名条目」这个结论不值得在账本里占一行（见上文格式一节）。

### 第二步：描述自动关联，然后候选排序

其余同名条目按描述相似度排序（token Jaccard；中文按字符 bigram 比较，
与共享搜索索引同一技巧）。

**≥ 90% 自动关联。** 当最佳同名候选的相似度达到
`SIMILARITY_AUTO_LINK_THRESHOLD`（0.9）时，措辞已足够接近，可认定两者
为同一技能，于是直接写入账本——无需询问，卡片显示来源仓库的方式与
原生安装相同。

**低于 90%——交由用户确认。** 该排序以待确认记录落盘，因此重启只是复活
它，而不必重算相似度；候选在卡片上以"确认关联"入口呈现。
对话框列出相似度最高的前 5 个候选并标注百分比——明确仅为参考而非证明：
fork 共享描述，高分也不能*认定*同一技能。不设相似度下限：低分只会让
候选沉到列表底部，因为把它藏掉可能恰好藏掉唯一正确的仓库（例如本地
描述缺失或措辞完全不同时）。用户选择之前不写入任何内容；确认结果与原生
安装无差别地写入账本。

为什么是 90% 而非更严格的下限？对发布快照（8993 个技能）的实测：549
个 slug 由 ≥2 个仓库发布，其中 171 个（31%）存在 ≥2 个*不同*仓库携带
逐字节相同的描述——涉及 525 个技能。每个描述完全相同的簇都跨越多个仓库
（fork 会原样照抄 frontmatter），因此完美的描述匹配在结构上就是歧义的：
它选中 fork 和选中本体的概率一样。90% 阈值刻意用罕见的静默误关联（错误的
来源链接、错误的更新流）换取：对真正相同的技能少弹大量确认框——而这恰恰是
用户本来也会确认的情况；低于 90% 的则仍交由用户判断。

## 在详情抽屉里重选与解除来源

详情抽屉的来源行即来源信息的呈现面：悬停提示说明已记录来源的建立方式
（经本应用从商店安装 / 已关联的第三方副本 / 未关联的本地安装），来源行
同时承载重选入口：

- **未关联且有候选** —— 「本地安装」标签变为与列表行相同的「确认关联」
  触发器，点击展开按相似度排序的同名候选。
- **已关联** —— 仓库链接旁一个安静的 chevron 打开「更改关联」弹层：
  置顶标示当前记录的来源、其余同名商店条目（`findLinkCandidates`，
  与建议同法排序但排除当前仓库，弹层打开时按需查询），以及出口。确认
  选择按原生安装写入（`via: "confirm"`）；用户选择或解除之前不写入
  任何内容。

**解除即拒绝。** 切断关联会把来源记录替换为一条待确认记录，被解除的仓库
列在 `repos` 里，自动关联层不会再把它链回去——用户的解除是一个决定，
不是缓存。记录已知的其余内容全部保留：候选、指纹与排序摘要都留着，
日后重新决定不必付代价。被解除的仓库仍会出现在手动候选里，因为重新
选回它是用户自己的重新认定行为。会话内同时清除建议备忘，下一次对账
立即重跑查找并给出其余候选。
